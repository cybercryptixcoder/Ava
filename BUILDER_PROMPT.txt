PART B. THE ORIGINAL SPECIFICATION (FULL DETAIL)
================================================

Build Ava as a proper GitHub repo (clear structure, documented, readable, tested). Every feature must actually work end to end once API keys are added: no placeholders, mocks in real code paths, TODO stubs or faked data.

B1. Configuration
- `.env.example` listing every key with a one-line comment (what it is, where to get it).
- Real environment variables take precedence over `.env`.
- Startup config check reporting present and missing keys and which features are disabled as a result.
- A missing optional key disables only its own feature.

B2. Core principle
- The intelligence plans ahead; the SYSTEM owns time, triggers, execution and enforcement.
- Nothing runs continuously.
- Every proactive message comes from a rule plus cited evidence.
- Ava returns wake requests as structured output, validated by a deterministic scheduler.
- Execution is done by fresh executor sessions that report plan-fit.
- Two-tier rules: a fixed constitution plus dynamic rules that need approval.

B3. Constitution, enforced in code
- Validator: cited IDs must exist; "because" lines must match stored state; failures are logged.
- No invented states of mind.
- Caps: morning brief plus at most 3 unprompted messages per day; quiet hours 23:00 to 08:00; nothing during class or exam blocks.
- Limits on dynamic rules (they can never raise caps, change quiet hours, edit the constitution, approve themselves, take external actions, or schedule beyond the wake budget).
- Explicit confirmation of every external action, each time, showing exactly what will be sent and to whom.
- Expiries and on/off switches on every dynamic rule.
- System-owned heartbeat and dead-man's switch.
- Daily model-call budget.
- Everything logged.

B4. Wakes
- Heartbeat every 3 hours (with lookahead that schedules precise wakes, e.g. 5 minutes after class ends).
- Scheduled wakes: deadlines at 14/3/1 days out; morning brief 08:30; evening plan 21:30; Sunday weekly review; executor sessions; validated planner requests.
- Event wakes (changes coalesce into one wake).
- An 8-step wake procedure: pull, update state, evaluate rules into candidates, internal actions, rank and draft with placeholders, validate, dispatch, record.
- Time-zone toggle (State College / Bangalore) recomputes all schedules.
- Dead-man alert after 6 waking hours without a successful wake.

B5. Rules
- Built-in: deadline horizon, free block, finish line (drafted/almost done 2+ days), stale project (important, untouched a week), follow-up (overdue commitment or reply owed).
- Dynamic rules: structured DSL with evidence, condition, action, expiry, approval tier, live stats.
- Shadow mode (replay over stored snapshots before approval).
- Self-pausing at precision below 0.4 after at least 5 messages.
- Caps of about 3 new rules per week and about 15 active.

B6. Life model
- Raw evidence separate from beliefs. Beliefs have provenance (stated, observed, inferred), confidence, evidence links, last confirmed, decay; inferred beliefs stay proposals until confirmed.
- Item types (task, project, commitment, open loop, goal, preference, saved item, event, rhythm), extensible schema.
- Active sensing: one question at a time when an unknown matters.
- Confirmation chips (now being replaced by auto-filing, see Part C).
- Check-off is immediate and cancels related wakes.

B7. Sources (plugin interface, each with on/off)
- On: voice/conversation, Google Calendar (OAuth, change notifications), ICS feeds, manual entry, ChatGPT/Claude export import (tolerant, date-weighted review queue).
- Off by default: Gmail sent mail only (extract HIS commitments and nothing about other people beyond what the commitment needs); laptop activity collector (local merge, sends sessions only); saved-items import; Wispr Flow via its official MCP server (never reuse the desktop app's session; if not possible, note it in the handoff).
- Staged compression for high-volume data.

B8. Executors
- Fresh sessions, produce artifacts (practice set, summary, draft, outline, plan), multi-session via the scheduler, never send anything externally.

B9. Reaching out
- Installable PWA, web push with action buttons, extensible channel layer.
- Message anatomy: first line is the point; a "because" line; 2 to 4 options; do it / not now / already done / less of this.
- (Original) morning brief spoken in under a minute plus screen. NOTE: Part C replaces this with the morning stack.

B10. Voice
- Async mode: big auto-expanding input, single-action send, paste, audio upload transcription, spoken replies with an autoplay setting.
- Live mode: WebRTC/WebSocket streaming, streaming STT with custom vocabulary, semantic end-of-turn with patience (he thinks out loud), barge-in, streaming LLM to streaming TTS, prompt caching, under about 800 ms latency measured in a dev panel, no fillers.
- TTS evaluation, word-level timestamps, tone control, same voice across modes, adapter layer, voice audition screen; speech adaptation.

B11. Interface (original; Part C changes the main screen)
- Typed, validated module vocabulary, in-place updates, speech-synced reveal, Ava knows canvas state.
- Screens: Today, Talk, Tasks and projects, Rules, What Ava knows, Messages, Log, Settings (sources, time zones/quiet hours, caps/budgets, voice audition, style notes, dev panel: latency, time simulation, model usage); first-run 5-step setup.

B12. Look and feel
- Vintage chronograph dial restraint. Dark theme first-class, automatic by local time plus override. Deliberate typography with tabular figures. Functional motion only; reduced-motion respected. Presence shown by a quiet indicator.
- AVOID the generic AI look: no orbs, gradient blobs, sparkle icons, purple-blue gradients; no cream plus terracotta; no near-black plus neon accent; no identical rounded-card grids with shadows; no all-caps eyebrow labels; no monospace small labels; no middle-dot metadata strings; no arrows on buttons; no chat-bubble-only layouts.

B13. How Ava talks

PART 3: AGENT BEHAVIOR FOR THE CARD STACK  [SERVER DONE; see Part D for details]
Threads: Ava groups items into a small number of top-level threads (e.g. "Midterm week", "Finish the SOP", "OS project"). A thread contains tasks, deadlines, commitments and open loops; subtasks nest under tasks. Ava maintains grouping herself as items arrive, using the existing extraction and planning paths. He can rename, merge or split threads by voice or text. Default about 7 active threads at most; if more, Ava groups further rather than showing more.
Cards: one thing that needs him, not one database item. Three kinds: Do (an action, e.g. the next step on a thread), Pick (a decision with 2 to 4 options), Know (a heads-up needing no action). Three layers, generated lazily only when opened: (1) one line saying what it is plus a short "why now"; (2) the thread's 3 to 5 relevant parts, or the options in detail; (3) the work itself or full detail: an executor artifact, a draft, notes.
The stack: an endpoint returning the current stack; priority-ordered by Ava using the existing rules, candidates and ranking logic; short and finite (about 5 cards on a normal day by default, configurable); when empty, an "all clear" state with Ava's next planned check-in; proactive messages that pass the validator become cards in the stack instead of separate message objects (constitution and validator unchanged).
Responses: Right/yes = do it or start it (spawn the executor if the card offers work). Left/not now = card leaves and comes back later; Ava decides when, no sooner than a configurable minimum delay; nothing is ever deleted by a swipe. Already done = updates state immediately and cancels related wakes. Stop suggesting this = the existing "less of this" cooldown. Already done and stop suggesting this are reached by long-press or by saying so, NOT as visible buttons.
Auto-filing with undo: when he talks, Ava files what he stated directly instead of asking him to accept each item; she asks first only when genuinely ambiguous or consequential (an inferred deadline, anything involving another person, anything external). After a brain dump the result is one Know card, e.g. "Filed 6 things, 1 needs you"; opening it shows what was filed with undo per item. Anything that still needs him gets its own card. Inferred (not stated) beliefs stay proposals but surface at most occasionally, as Pick cards, never as a list.
Fewer approvals: dynamic rule proposals no longer have their own approval surface on the main page; a rule that can message him and needs approval becomes a Pick card, at most about one a week, with the shadow-mode result as layer 2.
The brief is the stack: replace the written morning brief with the morning stack. If he opens Ava in the morning, the optional spoken version is a few sentences at most and points to the cards; it doesn't recite the day.
Quieter notifications: push only for time-sensitive cards (default cap 2 per day); text is just the card's one line. Everything else waits in the stack.
